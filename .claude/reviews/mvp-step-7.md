## Findings
- [MINOR] Schätzfuchs answer is not always mega size; the downsizing is not in DECISIONS.md — src/games/schaetzfuchs/view.ts: MEGA_CHARS=5 / XXL_CHARS=8 sets data-size to mega, xxl or xl. Any answer longer than 5 formatted characters (e.g. '42.195' m, '299.792.458') is shown in --fs-xxl or --fs-xl, not mega. DoD 5 and master plan §5 say 'Antwort in Mega-Größe'. The downsizing makes sense to avoid overflow, but the conventions require deviations to be recorded in DECISIONS.md, and this one is not.
- [MINOR] Blitz end timer sends 1000 for open tries but does not update the chips — src/games/blitz/play.ts: the stopEnd callback sends {i:k, ms:max} for every unreported try and then calls finish(null). finish emits 'done' with ms=null, so the view's onPhase never writes those 1000 values into results. The chips keep showing '–' and the pad shows 'FERTIG' with no time, although 1000 was reported to the host. On a first mount this is practically unreachable (dur leaves at least one show of slack). On resume (end = toLocal(endsAt)) it is the normal case. Display only; the payload is correct.
- [NOTE] playBlitz early click does not check the pad is in 'wait' — e2e/bots.ts: with o.early, the first click fires straight after center() and never confirms data-state==='wait'. In fast mode the minimum wait is about 150 ms. The commit body says an earlier version already hit the early click after go. A missed early start fails loudly (ms >= 1000 check and the CONTRACT 'early' state), so it cannot produce a false pass. It can become flaky under load, though, e.g. with 3 parallel pages in step 8. Consider waiting for 'wait' via raf waitForFunction before clicking.
- [NOTE] px-regex wording differs from the plan (stricter, fine) — The plan specified (^|[^\w.-])-?\d*\.?\d+px\b. The implementation uses (^|[^\w.])-?\d*\.?\d+px\b, which also counts a hyphen as a boundary. It catches strictly more, the self-test covers '-6px', 'translate(-3px, 0)' and '0 -.5px', and the non-matching controls stay non-matching. No action needed.
- [NOTE] Layout audit only covers one player — The no-scroll audit runs with the host alone. Schätzfuchs reveal (question card + answer + up to 8 guess rows), the hammer bars and the blitz strip grow with the number of players and could cause vertical scrolling in the game root at 390x844. Worth re-running the audit in the step-8 party run with several pages.
- [NOTE] Blitz pad and hammer react to pointer input only — blitz-pad and btn-hammer listen only to pointerdown. Keyboard activation (Enter/Space dispatches click) does nothing, and data-silent also suppresses the global tap sound. Matches the plan's 'Eingaben auf pointerdown'; just an accessibility gap to keep in mind.
- [NOTE] TRIES=3 is duplicated in blitz/view.ts — logic.ts keeps TRIES private and view.ts redefines it as 3. Deriving it from v.waits.length would avoid the two values drifting apart. Nit.
