## Findings
- [MAJOR] peer.ts host: reconnect() fires while the peer is being destroyed, leaving a stale broker registration — src/net/peer.ts:63-65 `peer.on('disconnected', () => { if (!peer.destroyed) peer.reconnect(); })`. In PeerJS 1.5.5 (node_modules/peerjs/dist/bundler.mjs:1737-1744, 1762-1772), destroy() calls disconnect() first, and disconnect() emits 'disconnected' while `_destroyed` is still false. `_destroyed = true` is only set after _cleanup(). So every peer.destroy() our code makes on the host peer (ep.close() at line 61, and fail() on 'timeout' or another error at lines 45-50) runs the handler. The handler sees destroyed===false and calls reconnect(). Because disconnected is true and destroyed is false at that moment, reconnect() runs _initialize(lastServerId) and socket.start(), which opens a NEW WebSocket for 'wgarcade-<CODE>' (lines 632-662, 1779-1783). _cleanup() then only calls socket.removeAllListeners() and never closes that raw WebSocket. Its onopen still schedules heartbeats every 5 s. Result: after ep.close() or a host timeout, the room code stays registered at the broker for as long as the tab is open. Joiners get no answer, so they hit 'timeout' after 10 s instead of a quick 'noroom', and one WebSocket plus its heartbeat leaks per closed endpoint. The plan's guard 'nur wenn der Peer nicht destroyed ist' does not work with PeerJS's event order. The fake in peer.test.ts hides this: FakePeer.destroy() only sets destroyed=true and never emits 'disconnected', and the reconnect test sets `peer.destroyed = true` by hand. Fix: keep our own flag (e.g. `let gone = false`), set it before every peer.destroy() in fail()/close(), and check it in the handler (`if (!gone && !peer.destroyed) peer.reconnect()`). Change FakePeer.destroy() to emit 'disconnected' before setting destroyed=true, as PeerJS 1.5.5 does, and add a test: ep.close() → reconnects stays 0.
- [MINOR] Protocol round-trip tests only one reject reason — src/net/protocol.test.ts: hostMsgs round-trips only `reason: 'full'`. 'started' and 'badname' are never checked to be accepted, so dropping one from REASONS in protocol.ts:19 would go unnoticed. DoD 2 still holds (all 7 types round-trip), but a parameterised case over all three reasons is cheap.
- [NOTE] Local host: send/close inside onConnection goes out before the ack — src/net/local.ts:45-55 emits arrivals (onConnection) synchronously BEFORE posting 'ack'. The plan wants this so the client's first hello arrives. But if a listener calls conn.send() or conn.close() synchronously in onConnection, the 'd'/'fin' is posted before the 'ack'. The client ignores everything before 'ack' (line 79), so it loses the message, or resolves with a conn the host has already closed. The §3.7 host runtime only replies after 'hello', so this does not happen today. Keep it in mind for engine/host.ts in step 5 (never send/close synchronously in onConnection), or post the ack before the emit and buffer nothing.
- [NOTE] crypto.randomUUID needs a secure context (relevant for testing over local WiFi) — src/net/local.ts:70 uses crypto.randomUUID(), as the master plan §3.1 specifies. Browsers expose it only in secure contexts (HTTPS or localhost/127.0.0.1). If the dev server is opened over plain http on a LAN IP (e.g. `vite --host`, opened on a phone in the WiFi, which the user's request hints at), randomUUID is undefined and join() throws a TypeError. Not a problem for E2E (127.0.0.1) or Pages (HTTPS). Worth remembering for step 5 (pid generation) and LAN testing.
- [NOTE] Peer endpoint close() tears down hard, without flush — src/net/peer.ts:61: HostEndpoint.close() only calls peer.destroy(). PeerJS then closes every DataConnection without {flush:true}, so messages sent just before ep.close() may be lost, and the arrivals emitter is not cleared. The local endpoint, by contrast, closes each conn through its Conn and sends fin. Not part of the step-2 DoD. Watch it if host.stop() in step 5 needs a final send.
- [NOTE] Extra module src/net/conn.ts is not in the master plan file list — conn.ts (shared Conn core for loopback, local and peer) is not listed in master plan §2. It is a small helper, fits 'kleine Module', and the impl commit body names it. An implementation detail, so no DECISIONS entry is needed.
